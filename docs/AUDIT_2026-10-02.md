## 2. Constats critiques (fiabilité des résultats)

1. ✅ **Les avertissements de fichier ne bloquaient pas la publication.**
   Un communiqué scanné annonçant 150 admis dont l'OCR n'en lit que 148
   pouvait être publié sans que personne ne confirme l'écart ; une fois la
   phase clôturée, les 2 candidats manquants auraient lu « vous n'y figurez
   pas ». Point ouvert depuis l'audit du 2026-08-17. Corrigé : la
   publication exige `confirmer_ecarts=true` (case à cocher dans l'admin),
   et la liste des écarts confirmés est journalisée dans `AuditLog`. Les
   colonnes de numéro d'ordre (« N° »), présentes dans presque tous les
   fichiers, ne déclenchent plus d'avertissement — sinon la case serait
   cochée par réflexe.
2. ✅ **Couleur de décision inversée sur mobile** (« NON ADMIS » en vert) —
   corrigé le 2026-10-01, et règles désormais identiques sur le web
   (`js/decision.js`), le mobile et le backend.
3. ✅ **Cache mémoire de secours non borné.** Si Redis tombe un jour de
   proclamation, chaque numéro de PV recherché ajoutait une entrée jamais
   supprimée (les entrées expirées ne partaient qu'à la relecture de la même
   clé) : croissance mémoire jusqu'à l'arrêt du processus. Borné à 10 000
   entrées (expirées d'abord, puis les plus anciennes).

## 3. Constats de sécurité

4. ✅ **XSS stocké dans l'espace candidat web** : le libellé des examens
   (saisi par les admins de chaque administration) était inséré sans
   échappement. Un compte admin compromis d'une administration pouvait
   exécuter du script chez tous les candidats et voler leur session
   (jeton valable 30 jours dans `localStorage`). Corrigé, ainsi que deux
   messages d'erreur d'API insérés sans échappement.
5. ⚠️ **Pas de révocation des jetons** (ouvert depuis le 2026-08-17) : un jeton
   candidat volé reste valable 30 jours, un jeton admin 1 heure. Piste
   simple : un compteur `version_jeton` sur le compte, incrémenté à la
   déconnexion / au changement de mot de passe, vérifié à chaque requête.
6. ✅ **Limitation de débit derrière un reverse proxy** (corrigé le même jour, voir `docs/DEPLOIEMENT.md`). `slowapi` identifie
   le client par l'IP de la connexion : derrière nginx, tous les visiteurs
   ont l'IP du proxy et partagent **un seul** quota de 30 requêtes/minute —
   le site entier serait bloqué en quelques secondes un jour de BAC (le
   `CMD` actuel du `backend/Dockerfile` n'active pas les en-têtes de proxy).
   À régler au déploiement : uvicorn avec `--proxy-headers --forwarded-allow-ips`
   (IP du proxy uniquement). Même remarque pour plusieurs workers : le
   compteur est en mémoire par processus (passer `storage_uri` sur Redis).
7. ⚠️ **Mots de passe de développement dans `docker-compose.yml`**
   (`faso_secret`) et port PostgreSQL publié sur l'hôte : acceptable en
   développement, à ne jamais réutiliser tel quel en production.

## 4. Déploiement — le projet n'est pas encore déployable en production

8. ✅ **Aucune configuration de production** (corrigé le même jour : `docker-compose.prod.yml`, `deploy/`, `docs/DEPLOIEMENT.md`, testé de bout en bout). `docker-compose.yml` est un
   environnement de développement (`--reload`, code source monté, base
   exposée). En production, le web appelle l'API sur la même origine
   (`js/api.js`) mais nginx ne sert que des fichiers statiques : **aucun
   appel `/api` n'aboutirait**. Il manque : un compose de production, une
   configuration nginx (fichiers statiques + `proxy_pass /api` + HTTPS), les
   en-têtes de sécurité (CSP, HSTS), et la procédure de sauvegarde
   (base + clé `CANDIDAT_ENCRYPTION_KEY`, dont la perte rend les données
   chiffrées illisibles).
9. ✅ **Tailwind via CDN en production** (remplacé le même jour par un CSS pré-généré, décision du développeur). La documentation Tailwind le
   déconseille : un script de compilation est téléchargé puis exécuté sur
   chaque téléphone pour générer le CSS (coût CPU sur les appareils bas de
   gamme, page sans style tant qu'il n'est pas chargé en 3G), et c'est une
   dépendance à un serveur étranger (souveraineté). Mesuré pendant cet
   audit : le CSS pré-généré de la page d'accueil pèse **20,7 Ko**. C'est une
   évolution de la stack verrouillée : à décider explicitement.
10. ✅ **Polices Poppins chargées depuis Google Fonts** (auto-hébergées le même jour) (déjà noté dans
    `docs/CHARTE_GRAPHIQUE.md`) : à auto-héberger avant la production.

## 5. App mobile

11. ⚠️ **Pas de clé de signature de production** (`android/key.properties`
    absent) : impossible de publier sur le Play Store tant qu'elle n'est pas
    créée et sauvegardée (procédure dans `mobile/docs/RELEASE.md`). iOS
    nécessite un compte Apple Developer (99 $/an) et un Mac avec Xcode.
12. ✅ **URL de production supposée** (désormais configurable au build, `--dart-define=API_BASE_URL`) : `https://api.fasoresultats.bf` est
    codée en dur (`lib/config/env.dart`) alors que le nom de domaine n'est
    pas encore réservé (voir ROADMAP § hébergement).
13. ℹ️ Dépendances Firebase embarquées mais inutilisées (notifications push
    non branchées) : alourdissent l'APK.
14. ℹ️ Pas encore testée sur un appareil réel (seulement tests + version web
    compilée).
